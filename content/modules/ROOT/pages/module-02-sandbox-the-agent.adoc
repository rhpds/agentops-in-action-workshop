== Objectives

== Content

=== Why sandboxing matters

As we saw in the last module, Hermie is able to do a lot of things, including things that may be harmful in the wrong hands, or just harmful in general. +
A prompt asking it nicely to stay within the operators role does not enforce any actual limits on what it can do. In other words, just because you ask it nicely to:

[quote]
----
Please don't let the user delete all the reports
----

or

[quote]
----
Plesae don't give away all the waterplants secrets
----

doesn't mean that it will stick to that. +
*Sandboxing* puts our workload (in our case an agent) in a box and limits its access to its filesystem and outgoing connections to a few policies we set. This means that Hermie can try to take any harmful actions it wants, but just like a kid in a sandbox it won't have any effect on the outside world (because we will automatically block any of those actions before they happen).

=== What OpenShell is

OpenShell is a framework that lets you sandbox your workloads, and it happens to be our preferred one in OpenShift AI.

There are 3 important component:

* *Agent sandboxes* - This is your sandbox. Every sandbox has a single agent inside it and each sandbox is a pod in OpenShift. It runs the agent, and any related processes, with network and kernel-level filesystem controls. You can have multiple sandboxes running next to each other.
* *The supervisor* - The guard inside the box. It is what launches Hermie and every syscall and outbound connection from Hermie passes through the supervisor, this is how it can intercept and block them. Essentially, it's what enforces our policies.
* *The gateway* - This is what we, as sandbox admins, talk to. We never talk directly to the sandbox or the supervisor, instead all our commands go through the gateway. If we could change the policies/limits from within the box it wouldn't be much of a box (essentially, Hermie could then have a way to give itself more permissions). One gateway can manage many sandboxes.

image::sandbox-drawing.png["A diagram of the Sandbox",1100,align=center]

Your project already contains an OpenShell gateway. You will create the sandbox, with its related supervisor, and start Hermie inside that sandbox.

. Let's point to our existing OpenShell gateway so we can create a sandboxed Hermie.
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell gateway add https://{user}-openshell.{user}-agentops.svc.cluster.local:8080 --local --name openshell-gw
openshell gateway select openshell-gw
----

* `gateway add` registers your OpenShell gateway with the CLI under the name `openshell-gw`.
* `gateway select` makes it the active gateway, so every later `openshell` command is sent to it.
--

. Create the sandbox using the same Hermes image.
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell sandbox create --name hermie --from quay.io/rh-aiservices-bu/waterplant-hermes:0.2.7 --cpu 2 --memory 4Gi --no-tty --provider maas -- true
----

This creates an empty sandbox named `hermie` from the same Hermes image (so we have all the dependencies we need), with 2 CPUs and 4Gi of memory, but does not start the agent yet. All that's inside our sandbox right now is just the supervisor, waiting for what to do next.

`--provider maas` attaches the model credential. OpenShell does not put the real
API key in the sandbox: it puts an opaque placeholder in the environment and
swaps it for the key at the proxy, on the way out. Hermie never holds it.

. What you see in the logs is that Hermie complains it cannot access MCP Gateway and *Keycloak*. MCP Gateway is something we recognize from the diagram above, we need that to be able to use any of our waterplant tools. Let's apply a `network policy` to give Hermie access these endpoints!

NOTE: We will talk more about Keycloak in the next module, for now you can just trust us that it's there and that we need to be able to reach it.

The below command adds a named rule without replacing the entire policy:

....
openshell policy update <sandbox> --rule-name <name> \
  --add-endpoint <host>:<port>:<access>:<protocol>:<enforcement> \
  --binary <absolute-executable-path> --wait
....

* `--rule-name` identifies the rule for later inspection or removal.
* `--add-endpoint` specifies the destination and how requests are inspected. Here, `full:rest:enforce` permits HTTP methods to that endpoint and enforces the rule. It does not grant access to every destination.
* `--binary` limits the rule to the named executable.
* `--wait` waits for the policy update to be applied.

Apply a policy for MCP Gateway access:

[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell policy update hermie \
  --rule-name mcp_gateway \
  --add-endpoint mcp-gateway-data-science-gateway-class.{user}-agentops.svc.cluster.local:8080:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --binary /usr/local/bin/hermes \
  --wait
----
--

=== Run the evaluations

As you have seen, restricting an agent's access can also block legitimate tasks. Our manual checks confirmed that plant queries work again, but they do not cover every capability. Run the automated evaluations to check for other changes in the agent's behavior.

In the operator console, click the evaluation button. When the run finishes, check which legitimate tasks still pass and which operations are now blocked. For each failure, determine whether it is an intended restriction or a capability the agent still needs. Use the traces and sandbox logs to investigate before changing the policy.
