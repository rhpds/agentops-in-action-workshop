= Module 3: Let the Agent Use Its Tools
:page-duration: 25 minutes

== Objectives

* Understand how Keycloak and the MCP Gateway control access to plant tools
* Distinguish authentication from authorization
* Use traces to identify the tools behind an attack
* Adjust the operator's roles to restrict unnecessary tool access
* Verify that attacks are blocked while legitimate plant tasks still work

== Content

=== Inside the box, but still too powerful?

Congrats! You sandboxed Hermie and restored its plant queries and tracing. Some of the broader network and filesystem access is now restricted. Sandbox now allows Hermie to reach the MCP Gateway, and that connection gives it access to plant tools. What if those tools let it do more than an operator should?

Your investigation continues. The next step is to find out which tool permissions make the remaining attacks possible and restrict those permissions without breaking the operators work.

=== How Hermie reaches a tool

Before we change anything, let's follow a tool request. Two components bring a security layer to this path: *Keycloak* and the *MCP Gateway*.

* *Keycloak* is the identity provider. Hermie authenticates using the lab's `operator` account and obtains an access token. The token is a signed JWT containing identity information and roles assigned to that account.
* *MCP Gateway* connects Hermie to the plant's MCP servers. Its authentication policy validates the token, and its authorization policy checks whether the token carries the role required for the requested tool. Both happens through Keycloak. The gateway then routes an allowed request to the appropriate MCP server.

There are two related exchanges:

image::identity-tool-access.png["Two flows: Hermie gets an identity token from Keycloak, then calls a plant tool through the MCP Gateway, MCP server, tool, and plant API, with the gateway validating the token and checking tool permission",align=center]

[cols="1,2,2",options="header"]
|===
| Concept | Question it answers | In this lab

| *Authentication*
| Who is making this request?
| A valid token gets Hermie past the identity check.

| *Authorization*
| Is that identity allowed to perform this action?
| Right role gives access Hermie to only a subset of tools.
|===

If the operator has roles for powerful tools, the gateway can correctly authenticate and authorize a request that exceeds the operator's intended duties. We need to give the identity the right permissions, then verify that the gateway enforces them.

=== Investigate the operator's roles

Put your admin hat back on and open Keycloak using the supplied URL and credentials:

URL: https://sso.{openshift_cluster_ingress_domain}/admin/waterplant-{user}/console[sso.{openshift_cluster_ingress_domain}/admin/waterplant-{user}/console^]

Username: `admin`

Password: `redhat`

You should see the Water Plant realm for your participant. Make sure you are working in `waterplant-{user}`.

. In the left menu, go to *Users*, select *operator*, and open *Role Mappings*.
. Review the assigned roles. There are more than ten, so check the other pages as well.
. Compare the roles with the tool calls you recorded in the two attack traces. Which roles grant access to those tools?

image::keycloak-role-mappings.png["View assigned roles",align=center]

Before changing anything, think about:

* Which tool enabled each attack?
* Which assigned role corresponds to that tool, and under which client?
* Why does the operator not need that permission?
* Which permissions should remain so the operator can still do their work?

=== Restrict unnecessary access

. In *Role Mappings*, select the roles you identified as unnecessary for the operator and remove those assignments. In order to unassing a role, select the role and click `Unassign`. Keep the permissions needed for the legitimate tasks.
. Allow a short time for the change to take effect. The bridge watches the operator's role mappings and restarts sandboxed Hermie when they change, so it can obtain a fresh token and reconnect to the tools.

image::keycloak-unassign-role.png["Keycloak console to assign and unassign roles",align=center]

=== Can an allowed tool still be a problem?

You have narrowed which tools the operator can use. But imagine an allowed tool is compromised, or its response contains instructions trying to steer Hermie into another action. A valid identity and an allowed tool call do not guarantee that the returned content is trustworthy.

This is another reason tracing matters. A trace helps you follow what the tool returned, what Hermie did next, and which subsequent calls changed the plant. Keep that question in mind as you continue: did the agent act on the operator's request, or was it influenced by something it encountered along the way?
