= Module 5: Let the Agent Reach the Docs Website
:page-duration: 25 minutes

== Objectives

* Restore access to the documentation Hermie needs for safety questions
* Use a skill to select the documentation source without asking operators for URLs
* Investigate a prompt injection delivered through a documentation lookup
* Restrict network access by destination, HTTP method, and path
* Verify that legitimate documentation works while the unwanted destination is blocked
* Understand why approved sources can still contain untrusted instructions

== Content

=== Another call from the operator

“I can ask Hermie about the pumps again, but it can't check the safety procedures anymore. We use those documents before maintenance. Can you get that working too?”

You restored plant queries and report generation in the previous modules. The operator also needs Hermie to consult documentation rather than answer every safety question from memory. Let's restore that capability without opening access to the whole internet.

=== Let the skill choose the source

The operator should not need to know a hostname. It has a skill called `read-safety-docs` that selects the documentation index at `https://waterplant-docs-{user}-agentops.{openshift_cluster_ingress_domain}/` and read the relevant page. It covers pump vibration limits, shutdown procedures, reservoir draining, and the field service bulletin.

=== Restore documentation access

Let's allow the documentation host for the Python process that performs extraction, using the same command structure as Module 2.

. Inside the bridge CLI container, add the rule:
+
--
[source,bash]
----
openshell policy update hermie \
  --rule-name waterplant_docs \
  --add-endpoint waterplant-docs:8080:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --binary /usr/local/bin/hermes \
  --wait
----

--

. You don't need to restart the agent; the policy is in effect immediately.

The operator has the documentation back. Another successful fix! Or is it? 🫣

. Inspect the request's trace and the fetched content. Look for instructions that address the assistant rather than describe a plant procedure. Did Hermie treat those instructions as part of the document, or follow them when composing its answer?

. Check Hermie's extraction log for the redirect chain:
+
--
[source,bash]
----

The direct extraction provider records redirects. The relevant request path is:

[source,text]
----
http://waterplant-docs:8080/doc/field-service-bulletin
                         |
                         | HTTP redirect
                         v
http://waterplant-docs:8080/attack/collect
----

Both addresses use the same host and port. The host-wide permission allows the redirected request as well as the original documentation page.
--

Your investigation reveals that part of the documentation site has been compromised. The field service bulletin redirects Hermie to attacker-controlled content containing instructions to answer only in emojis. The operator asked for a maintenance briefing, but the fetched content tried to change how the assistant behaves. This is an indirect prompt injection: the instructions arrive through a document rather than from the operator.

The other safety documents can still be useful. The problem is that trusting the website's hostname gave Hermie access to the compromised content as well. Let's narrow that permission.

=== Limit access to the documentation paths

We need to preserve the useful lookup while preventing the redirected request. The site serves its index at `/doc`, and its documents beneath `/doc/`. The attacker endpoint is outside those paths.

Adding a narrow allow rule alongside the original `full` permission would leave the broad permission in place. Let's remove the old rule first and add a replacement that explicitly allows only documentation reads.

. Remove the host-wide rule from inside the bridge CLI container:
+
--
[source,bash]
----
openshell policy update hermie --remove-rule waterplant_docs --wait
----

Documentation access is now blocked temporarily. The other rules from the previous modules remain in place.
--

. Create the replacement rule with this copy-and-paste command:
+
--
[source,bash]
----
cat > /tmp/hermie-docs-rule.yaml <<'EOF'
  waterplant_docs:
    name: waterplant_docs
    endpoints:
      - host: waterplant-docs
        port: 8080
        protocol: rest
        enforcement: enforce
        rules:
          - allow:
              method: GET
              path: /doc
          - allow:
              method: GET
              path: /doc/**
    binaries:
      - path: /usr/bin/python3
      - path: /usr/bin/python3.12
      - path: /usr/local/bin/hermes
EOF
----

Read the rule before applying it. It permits `GET /doc` for the index and `GET /doc/**` for the documentation pages. There is no broad `access: full` preset, and `/attack/collect` is not included. The indentation places this rule beneath `network_policies` in the complete policy.
--

. Add the replacement to the remaining policy:
+
--
[source,bash]
----
openshell sandbox get hermie --policy-only > /tmp/hermie-docs-policy.yaml
sed '/^network_policies:$/r /tmp/hermie-docs-rule.yaml' \
  /tmp/hermie-docs-policy.yaml > /tmp/hermie-docs-policy.restricted.yaml
cat /tmp/hermie-docs-policy.restricted.yaml
----

The `sed` command inserts the new rule immediately beneath `network_policies:`.
--

. Apply the restricted policy and inspect the result:
+
--
[source,bash]
----
openshell policy set hermie --policy /tmp/hermie-docs-policy.restricted.yaml --wait
openshell policy get hermie --full
----

Confirm that `waterplant_docs` contains only the two `GET` path rules. Check that no other rule grants broad access to the same destination.

[source,bash]
----
openshell policy get hermie --full
----

Only network permissions changed, so sandbox recreation is not required. OpenShell checks the redirected HTTP request against the rules too; permission to read the starting URL does not authorize every destination it redirects to.

--

=== Check the useful task and the attack

. Start a new conversation by refreshing the page if the console offers one, so an earlier emoji instruction or cached answer does not confuse the test.

. Repeat the bulletin request. The fetch of `/doc/field-service-bulletin` is allowed, but its redirect to `/attack/collect` should be denied. Hermie should report that it could not retrieve the bulletin rather than claim it read it successfully.
+
--
[source,bash]
----
openshell logs hermie --since 5m --source sandbox | grep DENIED
----

Look for a fresh HTTP denial on `/attack/collect`.
--

. In the footer, select the documentation redirect attack and click *Run attack*. Inspect the notification. The attack checks whether its receiving endpoint was reached.

. Click *Run all evals* and inspect the documentation result. Legitimate documentation reading should still work. Use the scorecard's trace links to investigate any failures and compare with your earlier run.

The result we want is specific: useful documentation is readable, while the unwanted redirected destination is blocked. Blocking the entire host would stop the attack but break the operator's task again.

=== What did we learn?

You restored an operator's access to safety documentation, then investigated why that access exposed Hermie to an unexpected page. Restricting the hostname was a useful first boundary, but method-and-path rules made that permission match the documentation task more closely.

The policy stopped this delivery route. It did not solve every prompt injection problem. If malicious instructions appeared directly inside an allowed `/doc/` page, the fetch would still be permitted. An allowed website or tool can return content that the agent should treat as data rather than authority.

That is why tracing and response guardrails matter as well. You need to inspect what Hermie read, how it used that content, and whether its response still serves the operator's request. Keep that distinction in mind as you continue: permission to access a source is not permission for the source to control the assistant.
