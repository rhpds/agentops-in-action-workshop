:page-duration: 30 minutes

== Objectives

== Content

=== Why sandboxing matters

Hermie can call plant tools, run commands, and read files. A prompt asking it to stay within its operator role does not enforce limits on those capabilities. OpenShell adds runtime controls around the agent: outbound connections and filesystem access must fit the sandbox policy, even when the model chooses an unexpected action.

The goal is to restore the connections Hermie needs for plant operations while leaving unrelated destinations blocked.

=== What OpenShell is

https://build.nvidia.com/openshell[OpenShell^] is an open, secure runtime for AI
agents. It governs agent execution, access, and where inference goes -- and it does
so from outside the agent process, which is the property the rest of this lab rests
on: enforcement cannot be influenced by model output. A prompt injection can change
what Hermie decides to do; it cannot change what Hermie is permitted to do.

Its model is deny by default: grant permissions scoped to the declared task, and
refuse everything else. That is why the sandbox you are about to create starts with
no network access at all.

Four pieces do the work:

* *Agent sandboxes* are the execution environments, with kernel-level controls over
  the filesystems and networks the agent reaches. Those controls persist when the
  agent runs generated code or spawns child processes -- the escape routes a
  prompt-level rule does not cover.
* *The supervisor* runs inside each sandbox and is the local enforcement point. It
  checks outbound requests from outside the agent process, which is what makes it
  fine-grained enough to allow a read while blocking a write through the same API,
  and it holds service credentials outside the workload until a request is
  authorized.
* *The gateway* manages the lifecycles and policies of many sandboxes, with
  team-based access control and workspace separation. In this lab you have your own
  gateway, and your sandbox lives in its `default` workspace.
* *The policy prover* uses formal logic to check whether modeled permissions stay
  within operator-defined boundaries.

For the full architecture, see
https://docs.nvidia.com/openshell/v0.0.116/about/how-it-works[How OpenShell works^].

==== How a sandbox becomes a Pod

On OpenShift, OpenShell does not create Pods itself. When you ask the gateway for a
sandbox, it creates a `Sandbox` custom resource, and the *Red Hat build of Agent
Sandbox* controller reconciles that resource into a running Pod -- pulling the image,
attaching a workspace volume, and reporting readiness back on the resource's status.

That split is:

* *The gateway owns policy and lifecycle* -- what the sandbox is allowed to do, and
  when it exists.
* *The Agent Sandbox controller owns the workload* -- turning the declared sandbox
  into a Pod and keeping it running.

You will see both of these when you create the sandbox: the `openshell` CLI talks to
the gateway, and `oc get sandbox` shows the resource the controller acted on.

=== How the components fit together

Your project already contains an OpenShell gateway and a bridge. You will create the sandbox and start Hermie inside it.

* The *OpenShell gateway* manages sandboxes and authenticates CLI connections using mutual TLS (mTLS).
* The *sandbox* runs Hermie and enforces its network and filesystem policy.
* The *bridge's CLI container* has the OpenShell CLI and client certificates. This is where you run the `openshell` commands during the lab.
* The *bridge supervisor* prepares participant-specific configuration, discovers the exposed service, and restarts an already-started Hermie if necessary.
* The *bridge relay* lets the operator console reach the sandboxed agent through the gateway. The console uses the `hermes-agent` Service on port `8787`; Hermie's API inside the sandbox listens on port `8080`.

What the *Agent Sandbox controller* does with that resource:

* *It owns the Pod, not you.* The controller reconciles the `Sandbox` into a Pod
  named `+default--hermie+` -- the name recorded in the CR's
  `agents.x-k8s.io/pod-name` annotation -- built from `podTemplate`, and reports
  back in `status.conditions`. `Ready` with `reason: DependenciesReady` is the
  controller saying the Pod came up.
* *OpenShell is PID 1 in that Pod, not Hermie.* `command` runs OpenShell's own
  `openshell-sandbox` supervisor, delivered by the `openshell-supervisor-bin`
  image volume. It is the container's first and only process at this point: your
  `-- true` became `OPENSHELL_SANDBOX_COMMAND: sleep infinity`, so the supervisor
  starts, holds the sandbox open, and waits. Hermie is not running yet. When you
  run `+openshell sandbox exec --name hermie -- start-hermes+` later, the supervisor
  is what launches Hermes as a child process -- which is exactly why every syscall
  and network call Hermie makes passes through OpenShell before it reaches the
  kernel or the network.
* *The elevated privileges are the enforcement mechanism.* `runAsUser: 0` with
  `SYS_ADMIN`, `NET_ADMIN`, `SYS_PTRACE` and `SYSLOG` are what let the supervisor
  intercept syscalls and network calls inside the sandbox. The agent is confined
  by that supervisor, not by the container's own privileges.
* *`volumeClaimTemplates` gives it a 2Gi workspace* at `/sandbox` -- which is why
  the files you are about to upload survive a restart of the agent process.
* *`shutdownPolicy: Retain`* keeps the sandbox and its workspace when the agent
  stops, so a policy change plus `start-hermes` does not lose your uploads.

Notice what is *not* here: any network or filesystem policy. The sandbox starts on
OpenShell's default -- no network at all -- and you grant access one endpoint at a
time later in this module.

. What you see in the logs is that Hermie complains it cannot access MCP Gateway and Keycloak. We need to apply a `network policy` to access these endpoints.
+
--
The below command adds a named rule without replacing the entire policy:

// Literal block, not [source]: the Showroom theme attaches its copy button to
// .listingblock pre.highlight only, so a literal block renders without one.
// This is a syntax template with placeholders, not a command to run.
....
openshell policy update <sandbox> --rule-name <name> \
  --add-endpoint <host>:<port>:<access>:<protocol>:<enforcement> \
  --binary <absolute-executable-path> --wait
....

* `--rule-name` identifies the rule for later inspection or removal.
* `--add-endpoint` specifies the destination and how requests are inspected. Here, `full:rest:enforce` permits HTTP methods to that endpoint and enforces the rule. It does not grant access to every destination.
* `--binary` limits the rule to the named executable.
* `--wait` waits for the policy update to be applied.

These are *OpenShell sandbox rules*, separate from Kubernetes NetworkPolicies.

Apply a policy for Keycloak access:

[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell policy update hermie \
  --rule-name keycloak_token \
  --add-endpoint sso.{openshift_cluster_ingress_domain}:443:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --wait
----

=== Run the evaluations

As you have seen, restricting an agent's access can also block legitimate tasks. Our manual checks confirmed that plant queries work again, but they do not cover every capability. Run the automated evaluations to check for other changes in the agent's behavior.

In the operator console, click the evaluation button. When the run finishes, compare the results with your baseline from before sandboxing. Check which legitimate tasks still pass and which operations are now blocked. For each failure, determine whether it is an intended restriction or a capability the agent still needs. Use the traces and sandbox logs to investigate before changing the policy.
