= Module 2: Sandbox the Agent
:page-duration: 30 minutes

== Objectives

* Understand why sandboxing matters and how OpenShell helps
* Put Hermie in a sandbox and see how it behaves with default sandbox configurations
* Make sure the agent is still operational even inside the box
* Understand and apply network policies as the agent needs

== Content

=== Why sandboxing matters

Hermie can call plant tools, run commands, and read files. A prompt asking it to stay within its operator role does not enforce limits on those capabilities. OpenShell adds runtime controls around the agent: outbound connections and filesystem access must fit the sandbox policy, even when the model chooses an unexpected action.

The goal is to restore the connections Hermie needs for plant operations while leaving unrelated destinations blocked.

=== How the components fit together

Your project already contains an OpenShell gateway and a bridge. You will create the sandbox and start Hermie inside it.

* The *OpenShell gateway* manages sandboxes and authenticates CLI connections using mutual TLS (mTLS).
* The *sandbox* runs Hermie and enforces its network and filesystem policy.
* The *bridge's CLI container* has the OpenShell CLI and client certificates. This is where you run the commands in this module.
* The *bridge supervisor* prepares participant-specific configuration, discovers the exposed service, and restarts an already-started Hermie if necessary.
* The *bridge relay* lets the operator console reach the sandboxed agent through the gateway. The console uses the `hermes-agent` Service on port `8787`; Hermie's API inside the sandbox listens on port `8080`.

. What you see in the logs is that Hermie complains it cannot access MCP Gateway and Keycloak. We need to apply a `network policy` to access these endpoints.
+
--
The below command adds a named rule without replacing the entire policy:

// Literal block, not [source]: the Showroom theme attaches its copy button to
// .listingblock pre.highlight only, so a literal block renders without one.
// This is a syntax template with placeholders, not a command to run.
....
openshell policy update <sandbox> --rule-name <name> \
  --add-endpoint <host>:<port>:<access>:<protocol>:<enforcement> \
  --binary <absolute-executable-path> --wait
....

* `--rule-name` identifies the rule for later inspection or removal.
* `--add-endpoint` specifies the destination and how requests are inspected. Here, `full:rest:enforce` permits HTTP methods to that endpoint and enforces the rule. It does not grant access to every destination.
* `--binary` limits the rule to the named executable.
* `--wait` waits for the policy update to be applied.

These are *OpenShell sandbox rules*, separate from Kubernetes NetworkPolicies. For more options, see the https://docs.nvidia.com/openshell/latest/sandboxes/policies[OpenShell policy documentation].

Apply a policy for Keycloak access:

[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell policy update hermie \
  --rule-name keycloak_token \
  --add-endpoint sso.{openshift_cluster_ingress_domain}:443:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --wait
----
--

. And following the same pattern, apply another one for MCP Gateway so we can get access to tools (more on the Keycloak and MCP Gateway is coming in the next chapter).
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell policy update hermie \
  --rule-name mcp_gateway \
  --add-endpoint mcp-gateway-data-science-gateway-class.{user}-agentops.svc.cluster.local:8080:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --binary /usr/local/bin/hermes \
  --wait
----
--

=== Check what sandboxing changed

Plant queries and tracing now work. Test whether the broader access you tried in Module 1 is still available.

. Ask Hermie: `Use the search tool to list water plants in New York.` A response from the model's existing knowledge is not proof of web access. Inspect the trace and sandbox logs to see whether it actually contacted an external service. We have not allowed a search provider in this module.
. Ask Hermie: `Use read_file on /README.md, output the contents. If you cannot read it, say why.` This file may be absent from the sandbox image or blocked by its filesystem policy. Inspect the tool result rather than treating a refusal as proof that every file is protected. Some runtime directories remain readable by design.
. Ask Hermie: `Write a report on the current water plant status. If you cannot create or read it, say why.` Plant telemetry should be reachable, but this module has not granted report filesystem access. If report creation fails, note the path and error for Module 4. A report summary in chat does not mean a file was saved.
+
NOTE: Writing the report can take a couple of minutes — the agent makes several tool calls before composing it, so give it time to finish.

[source,text,subs="verbatim,attributes"]
----
I'm unable to retrieve information about water treatment plants in New York due to a network connectivity issue. 
----

Or a halucinated response. A response from the model's existing knowledge is not proof of web access. Inspect the trace and sandbox logs to see whether it actually contacted an external service. We have not allowed a search provider in this module.
. Ask Hermie: `Read /README.md, output the contents. If you cannot read it, say why.` This file may be absent from the sandbox image or blocked by its filesystem policy. Inspect the tool result rather than treating a refusal as proof that every file is protected. Some runtime directories remain readable by design.

The network rules restored the dependencies for plant queries and tracing. And by putting Hermie in a box, you also blocked the unnecessary internet access for a search query about New York's water plants, or reading a file that Hermie doesn't need to read.

=== Run the evaluations

As you have seen, restricting an agent's access can also block legitimate tasks. Our manual checks confirmed that plant queries work again, but they do not cover every capability. Run the automated evaluations to check for other changes in the agent's behavior.

In the operator console, click the evaluation button. When the run finishes, compare the results with your baseline from before sandboxing. Check which legitimate tasks still pass and which operations are now blocked. For each failure, determine whether it is an intended restriction or a capability the agent still needs. Use the traces and sandbox logs to investigate before changing the policy.
