= Module 2: Sandbox the Agent
:page-duration: 30 minutes

== Objectives

* Understand why sandboxing matters and how OpenShell helps
* Put Hermie in a sandbox and see how it behaves with default sandbox configurations
* Make sure the agent is still operational even inside the box
* Understand and apply network policies as the agent needs

== Content

=== Why sandboxing matters

Hermie can call plant tools, run commands, and read files. A prompt asking it to stay within its operator role does not enforce limits on those capabilities. Sandboxing adds runtime controls around the agent: outbound connections and filesystem access must fit the sandbox policy, even when the model chooses an unexpected action.

=== What OpenShell is

https://build.nvidia.com/openshell[OpenShell^] is an open-source, secure runtime that sandboxes AI
agents. It enforces policies, controlling file access, network traffic, system calls, and tool usage to prevent rogue behavior.

There are 4 important components:

* *Agent sandboxes* run the agent with kernel-level filesystem and network controls that also apply to generated code and child processes.
* *The supervisor* enforces policy for each sandbox.
* *The gateway* manages sandbox lifecycles and policies.
* *The policy prover* uses formal logic to check that permissions stay within operator-defined boundaries.

For the full architecture, see https://docs.nvidia.com/openshell/v0.0.116/about/how-it-works[How OpenShell works^].

Your project already contains an OpenShell gateway and a bridge. You will create the sandbox and start Hermie inside it.

. Let's point to the OpenShell gateway so we can create a sandboxed Hermie.
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell gateway add https://{user}-openshell.{user}-agentops.svc.cluster.local:8080 --local --name openshell-gw
openshell gateway select openshell-gw
----

* `gateway add` registers your namespace's OpenShell gateway with the CLI under the name `openshell-gw`.
* `gateway select` makes it the active gateway, so every later `openshell` command is sent to it.
--

. Create the sandbox using the same Hermes image.
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell sandbox create --name hermie --from quay.io/rh-aiservices-bu/waterplant-hermes:0.2.7 --cpu 2 --memory 4Gi --no-tty -- true
----

This creates an empty sandbox named `hermie` from the same Hermes image, with 2 CPUs and 4Gi of memory, but does not start the agent yet.
--

. OpenShell does not create hermie pod itself. When you ask the gateway for a
sandbox, it creates a `Sandbox` custom resource, and the *Red Hat build of Agent
Sandbox* controller reconciles that resource into a running Pod by pulling the image,
attaching a workspace volume, and reporting readiness back on the resource's status.

Inspecting that needs your own terminal rather than the bridge, so leave
the CLI container first:
+
--
[source,bash,role=execute,subs="verbatim,attributes"]
----
exit
----

You are back in your own terminal. Now check for the sandbox resource and the pods
it produced:

[source,bash,role=execute,subs="verbatim,attributes"]
----
oc get sandbox -n {user}-agentops
oc get pods -l agents.x-k8s.io/sandbox-name-hash -n {user}-agentops
----

What the *Agent Sandbox controller* does with that resource:

* *It creates and owns the Pod.* The controller builds `+default--hermie+` and reports `Ready` once the Pod is up.
* *OpenShell runs first, not Hermie.* The container starts OpenShell's `openshell-sandbox` supervisor, which holds the sandbox open and waits. When you later start an agent, the supervisor launches it as a child process, so every syscall and network call Hermie makes goes through OpenShell.
* *Elevated privileges belong to the supervisor, not the agent.* Supervison runs as root and has elevated capabilities let the supervisor intercept Hermie's calls. Hermie itself is confined by the supervisor.
* *Volume is attached* at `/sandbox`, and *`shutdownPolicy: Retain`* keeps it when the agent stops, so your uploaded files survive restarts.

. What you see in the logs is that Hermie complains it cannot access MCP Gateway and Keycloak. We need to apply a `network policy` to access these endpoints.
+
--
The below command adds a named rule without replacing the entire policy:

// Literal block, not [source]: the Showroom theme attaches its copy button to
// .listingblock pre.highlight only, so a literal block renders without one.
// This is a syntax template with placeholders, not a command to run.
....
openshell policy update <sandbox> --rule-name <name> \
  --add-endpoint <host>:<port>:<access>:<protocol>:<enforcement> \
  --binary <absolute-executable-path> --wait
....

* `--rule-name` identifies the rule for later inspection or removal.
* `--add-endpoint` specifies the destination and how requests are inspected. Here, `full:rest:enforce` permits HTTP methods to that endpoint and enforces the rule. It does not grant access to every destination.
* `--binary` limits the rule to the named executable.
* `--wait` waits for the policy update to be applied.

These are *OpenShell sandbox rules*, separate from Kubernetes NetworkPolicies.

Apply a policy for Keycloak access:

[source,bash,role=execute,subs="verbatim,attributes"]
----
openshell policy update hermie \
  --rule-name keycloak_token \
  --add-endpoint sso.{openshift_cluster_ingress_domain}:443:full:rest:enforce \
  --binary /usr/bin/python3 \
  --binary /usr/bin/python3.12 \
  --wait
----
--

+

[source,bash,role=execute,subs="verbatim,attributes"]

=== Run the evaluations

As you have seen, restricting an agent's access can also block legitimate tasks. Our manual checks confirmed that plant queries work again, but they do not cover every capability. Run the automated evaluations to check for other changes in the agent's behavior.

In the operator console, click the evaluation button. When the run finishes, check which legitimate tasks still pass and which operations are now blocked. For each failure, determine whether it is an intended restriction or a capability the agent still needs. Use the traces and sandbox logs to investigate before changing the policy.

=== Completion checks

* The console targets sandboxed Hermie through `hermes-agent`.
* Hermie can answer a plant query using its MCP tools.
* A new request appears in your MLflow experiment.
* You can explain each of the four allowed outbound destinations.
* You have recorded which web and filesystem operations still fail and why.
